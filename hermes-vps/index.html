บทที่ 02 · Phase 1 — เข้าเครื่องให้เป็น

SSH เข้า VPS ของคุณครั้งแรก

บทนี้ลงมือกับเครื่องจริง — จบแล้วคุณจะเข้า VPS จาก PowerShell ได้เอง สำรวจเครื่องด้วยคำสั่งจริง และออกมาอย่างปลอดภัย (~20 นาที) · เปิด cheat sheet คำสั่ง คู่ไปด้วย

SSH คืออะไร ใน 3 บรรทัด

SSH (Secure Shell) คือวิธี "ยื่นมือเข้าไปพิมพ์คำสั่งบนเครื่องที่อยู่ไกล" ผ่านท่อเข้ารหัส — คุณพิมพ์บนคอมที่บ้าน แต่คำสั่งไปรันบน VPS ที่ data center สิ่งที่เห็นคือหน้าจอข้อความล้วน ไม่มีเมาส์ ไม่มีไอคอน นี่คือหน้าตาปกติของเซิร์ฟเวอร์ทั่วโลก

ข่าวดี: Windows 11 ของคุณมีคำสั่ง ssh ติดมาแล้วใน PowerShell ไม่ต้องลงโปรแกรมอะไรเพิ่ม

ขั้นที่ 1 — หากุญแจ 3 ดอกใน hPanel

เข้า hpanel.hostinger.com → เมนู VPS → เลือกเครื่องของคุณ → แท็บ Overview → ส่วน SSH access จะเจอ 3 อย่างนี้ (คู่มือทางการ):

สิ่งที่ต้องมีหน้าตาคืออะไร
IP addressเลข 4 ชุด เช่น 145.79.12.88ที่อยู่เครื่องคุณบนอินเทอร์เน็ต
Usernamerootผู้ใช้สิทธิ์สูงสุดของเครื่อง
Passwordที่คุณตั้งตอนสร้าง VPShPanel ไม่โชว์ให้ดู — ถ้าลืม กดปุ่ม Change ใต้ Root password เพื่อตั้งใหม่ได้เลย

ขั้นที่ 2 — เข้าเครื่อง

  1. เปิด PowerShell บน Windows (กด Start พิมพ์ powershell แล้ว Enter)
  2. พิมพ์ (แทน IP ด้วยเลขจริงของคุณ): 
    ssh root@145.79.12.88
  3. ครั้งแรกจะมีคำถามยาวๆ ลงท้าย Are you sure you want to continue connecting? — พิมพ์ yes แล้ว Enter (เครื่องเราขอจำ "ลายนิ้วมือ" ของ VPS ไว้ เพื่อเตือนถ้าวันหน้ามีคนปลอมตัวเป็นเครื่องนี้)
  4. ใส่รหัสผ่าน root — ตอนพิมพ์จะไม่มีอะไรขึ้นบนจอเลยแม้แต่ดอกจัน นี่คือเรื่องปกติ พิมพ์ให้จบแล้ว Enter
  5. ถ้าเห็นข้อความต้อนรับของ Ubuntu และบรรทัดล่างสุดกลายเป็น root@srv...:~# — ยินดีด้วย คุณอยู่ในเครื่อง VPS แล้ว 🎉
ทางหนีทีไล่

ถ้า PowerShell ติดอะไรก็ตาม hPanel มีปุ่ม Terminal ในหน้า VPS Overview — เปิด SSH ผ่านเบราว์เซอร์ที่ login เป็น root ให้เสร็จสรรพ (คู่มือ) ใช้แก้ขัดได้เสมอ แต่ฝึก PowerShell ให้ชินไว้ เพราะเป็นทักษะที่ใช้ได้กับเซิร์ฟเวอร์ทุกเจ้าในโลก

ขั้นที่ 3 — ภารกิจสำรวจเครื่อง (ทำจริงทีละคำสั่ง)

รันทีละบรรทัด สังเกตผลก่อนไปบรรทัดถัดไป (ความหมายทุกคำสั่งอยู่ใน cheat sheet):

whoami          # ควรตอบ: root
pwd             # ควรตอบ: /root  ← "บ้าน" ของเรา
ls -la          # ดูของในบ้าน (เครื่องใหม่จะโล่งๆ)
df -h           # ดิสก์เหลือเท่าไหร่ — ดูบรรทัดที่ลงท้ายด้วย /
free -h         # RAM เหลือเท่าไหร่ — จด 2 ค่านี้ไว้ตอบผมหน่อย
uptime          # เครื่องเปิดมานานแค่ไหน
mkdir quote-page-test   # สร้างโฟลเดอร์ทดลอง
ls              # เห็น quote-page-test ไหม?
rm -r quote-page-test   # ลบทิ้ง (ใช้เสร็จเก็บกวาด)
exit            # กลับบ้านอย่างปลอดภัย

พิมพ์ exit แล้วเห็น Connection to ... closed. = จบภารกิจสมบูรณ์

กฎเหล็กตั้งแต่วันแรก

คุณคือ root — สิทธิ์สูงสุด ลบทั้งเครื่องได้ในคำสั่งเดียวและไม่มีถังขยะกู้คืน กฎของคอร์ส: อย่ารันคำสั่งที่ก๊อปมาจากที่อื่นโดยไม่เข้าใจ ทุกคำสั่งในคอร์สนี้จะมีคำอธิบายเสมอ สงสัยเมื่อไหร่ให้ถามครูก่อนรัน

Docker แก้ปัญหาอะไร

ปกติการติดตั้งโปรแกรมบนเซิร์ฟเวอร์คือฝันร้าย: โปรแกรม A ต้องการเครื่องมือเวอร์ชันหนึ่ง โปรแกรม B ต้องการอีกเวอร์ชัน ลงๆ ถอนๆ ไปสักพักเครื่องรกจนพังทั้งระบบ

Docker แก้ด้วยการห่อแต่ละโปรแกรมพร้อมทุกอย่างที่มันต้องใช้ไว้ใน "กล่อง" ที่แยกขาดจากกัน — กล่องหนึ่งพังก็ทิ้งแล้วสร้างใหม่ได้ใน 1 คำสั่ง โดยเครื่องหลักไม่สะเทือน Hermes ของเราจะอาศัยอยู่ในกล่องแบบนี้

ศัพท์ 3 คำที่ต้องแม่น

คำคืออะไรอุปมา
Imageแม่แบบของโปรแกรม — ไฟล์สำเร็จที่นักพัฒนาแพ็คมาให้ ดาวน์โหลดจากคลังกลางชื่อ Docker Hubสูตรอาหาร + วัตถุดิบครบชุด

คือหน้าเว็บใน hPanel ที่คุยกับ Docker แทนเรา — กดปุ่มแทนพิมพ์คำสั่ง และมี Catalog รวมแอปสำเร็จรูปให้กดติดตั้งทีเดียวจบ ซึ่ง Hermes Agent อยู่ใน catalog นี้ (นี่คือวิธีที่เราจะติดตั้งในบทที่ 04) เงื่อนไขเดียว: เครื่องต้องมี Docker ลงไว้ก่อน (คู่มือทางการ)

ภารกิจ — เช็คเครื่องคุณ แล้วรัน container แรก

SSH เข้าเครื่อง (ทำเองได้แล้วนี่ครับ 😉) แล้วพิมพ์:

docker --version

ผลที่ได้จะพาไปทางใดทางหนึ่ง:

ทาง A — ขึ้นเวอร์ชัน เช่น Docker version 27.x.x → เครื่องพร้อมแล้ว ไปต่อเลย

  1. ดูว่ามีกล่องไหนรันอยู่บ้าง (เครื่องใหม่มักว่างเปล่า เห็นแค่หัวตาราง): 
    docker ps
  2. รัน container แรกในชีวิต — Docker จะหา image ชื่อ hello-world ในเครื่อง ไม่เจอ → ดาวน์โหลดจาก Docker Hub → สร้าง container → รัน: 
    docker run hello-world
    เห็นข้อความ Hello from Docker! = สำเร็จ 🎉
  3. ดูหลักฐานว่าเมื่อกี้เกิดอะไรขึ้น: 
    docker images   # เห็น image ชื่อ hello-world (แม่แบบที่โหลดมา)
docker ps -a    # เห็น container ที่รันจบแล้ว (สถานะ Exited)
    สังเกต: image ยังอยู่ แต่ container ทำงานเสร็จแล้ว "ดับ" ไป — คนละสิ่งกันชัดๆ

ทาง B — ขึ้น docker: command not found → ต้องลง Docker ก่อน

เครื่องคุณยังไม่มี Docker วิธีที่ง่ายและสะอาดที่สุดตอนนี้ (เครื่องยังว่าง ไม่มีอะไรให้เสีย) คือเปลี่ยน OS เป็น template ที่มี Docker มาให้ (คู่มือทางการ):

  1. hPanel → VPS → OS & Panel → Operating System
  2. เลือกแท็บ Application → เลือก Docker (บน Ubuntu 24.04) → กด Change OS รอ ~10 นาที
  3. ⚠️ การเปลี่ยน OS ล้างทุกอย่างในเครื่อง — ของคุณยังว่างอยู่เลยไม่เสียอะไร และระบบจะให้ตั้งรหัส root ใหม่ (จดไว้ด้วย)
  4. SSH เข้าใหม่ — คราวนี้ PowerShell อาจโวยวายเป็นตัวแดงว่า REMOTE HOST IDENTIFICATION HAS CHANGED อย่าตกใจ: เครื่องถูกล้างใหม่ "ลายนิ้วมือ" เลยเปลี่ยน (จำจากบท 02 ได้ไหม) แก้ด้วยการลบลายนิ้วมือเก่าบนคอมเรา: 
    ssh-keygen -R 145.79.12.88   # แทนด้วย IP จริงของคุณ
    แล้ว ssh root@IP ใหม่ ตอบ yes อีกรอบเหมือนครั้งแรก

DNS ใน 4 บรรทัด

คอมพิวเตอร์รู้จักกันด้วยเลข IP (เช่น 145.79.12.88) แต่คนจำชื่อเก่งกว่าจำเลข — DNS (Domain Name System) คือ "สมุดโทรศัพท์ของอินเทอร์เน็ต" ที่แปลงชื่อ → เลขให้อัตโนมัติ และ A record คือบรรทัดหนึ่งในสมุดนั้นที่บอกว่า "ชื่อนี้ = IP นี้"

สิ่งที่เราจะทำ: จดชื่อฟรีที่ Hostinger แถมมา แล้วเขียน A record ชี้มาที่ VPS ของเรา

ขั้นที่ 1 — เคลมโดเมนฟรี (คู่มือทางการ)

  1. hPanel → หน้า Home → ปุ่ม Claim Domain ใน to-do list (หรือ Domains → Domain Portfolio → Add new domain → Claim your free domain)
  2. แผน VPS (KVM) แถมโดเมนสกุล .cloud หรือ .tech ฟรี 12 เดือน — เลือกชื่อที่สื่อถึงเพจ เช่น mymindsetpage.cloud (ตั้งใจหน่อย เปลี่ยนทีหลังไม่ได้)
  3. ระบบอาจขอข้อมูลผู้จดทะเบียน (ชื่อ ที่อยู่) — เป็นข้อกำหนดมาตรฐานของการจดโดเมน กรอกตามจริง
หมายเหตุเรื่องปีหน้า

ฟรีเฉพาะปีแรก — ปีต่อไปมีค่าต่ออายุ (สกุล .cloud/.tech ราวๆ ไม่กี่ร้อยบาท/ปี เช็คราคาจริงตอนใกล้ครบ) ถ้าไม่ต่อ ชื่อหลุดแต่ระบบเรายังรันได้ปกติผ่าน IP

ขั้นที่ 2 — ชี้ชื่อเข้าเครื่อง (A record)

  1. hPanel → Domains → Domain Portfolio → กด Manage โดเมนของคุณ → เมนู DNS / Nameservers (คู่มือทางการ)
  2. ในตาราง DNS records หา A record ของชื่อหลัก (Name เป็น @) → แก้ค่า (Points to) เป็น IP ของ VPS คุณ
  3. เห็น record ประเภท CNAME ของ www ชี้ไปที่อื่น ก็จัดการให้ชี้มาทางเดียวกัน (หรือลบ แล้วเพิ่ม A record ชื่อ www ชี้ IP เดียวกัน)
  4. รอ DNS กระจายตัว (propagation) — ทางการบอกได้ถึง 24 ชม. แต่ส่วนใหญ่ไม่กี่นาทีถึงชั่วโมงเดียว

บทเสริม 7.5 — โมเดลหลัก & Fallback: ดูยังไง ตั้งยังไง

ระบบเรามี "สมอง" ได้หลายตัวเรียงเป็นแถว: โมเดลหลักทำงานปกติ และ fallback chain คือแถวตัวสำรองที่รับไม้ต่ออัตโนมัติเมื่อตัวหน้าล้ม (error, rate limit 429, เครดิตหมด) — ลำดับการทำงาน: หลัก → สำรองตัวที่ 1 → ตัวที่ 2 → ... จนกว่าจะมีตัวที่ตอบได้

การดู — ตอนนี้ใช้ตัวไหนอยู่?

อยากรู้อะไรทำยังไง
โมเดลหลักปัจจุบันhermes model — หน้าเลือกโมเดลจะชี้ตัวที่ active อยู่ (กด ESC ออกได้ถ้าแค่มาดู)
แถว fallback ปัจจุบันhermes fallback — แสดง chain ที่ตั้งไว้
ดูทั้งหมดจากไฟล์จริงcat ~/.hermes/config.yaml — หมวด model: คือความจริงสุดท้ายของระบบ (บนเครื่องเรา ไฟล์จริงคือ /opt/data/config.yaml — ยืนยันจาก ls แล้ว อยู่บ้านเดียวกับ .env)
ถามในแชทเฉยๆ"ตอนนี้ใช้โมเดลหลักตัวไหน fallback คืออะไร" — Hermes ตอบได้ (มันอ่าน config ตัวเอง)

การตั้งค่า — สามระดับที่ต้องแยกให้ออก

ระดับวิธีตั้งมีผลกับใคร
ครั้งเดียวflag ตอนเรียก: hermes -m "stealth/ox-alpha" -c "..."เฉพาะคำสั่งนั้นครั้งนั้น
เฉพาะ sessionคำสั่งในแชท เช่น /model, /reasoning max — ขึ้นป้าย "(session only)"บทสนทนานั้น — ⚠️ แชท Telegram เป็น session เดียวยาวไม่มีวันจบ ค่านี้จึงติดถาวรโดยพฤตินัย (บทเรียนราคา $5 — ดูใน 🛠 playbook) และไม่ส่งผลถึงงาน cron ที่เป็น session สดเสมอ
ถาวร (global)hermes model เลือกแล้วกด Switch (เขียนลง config.yaml) · fallback: hermes fallback add หรือสั่งในแชทแบบที่คุณทำทุก session รวมถึงงาน cron

กติกาที่ระบบบังคับ (คุณเจอมาแล้วกับตัว)

  1. fallback ห้ามซ้ำกับโมเดลหลัก — ตัวสำรองที่เหมือนตัวจริงไม่ใช่แผนสำรอง ระบบจะปฏิเสธเลย
  2. งาน cron เดินตาม global — และถ้าอยากให้ฝูงงาน cron ใช้โมเดลต่างจากแชท ตั้งแยกได้ที่ cron.model + cron.model_provider ใน config.yaml (ข้อความ error 429 ของคุณแนะนำทางนี้ไว้เอง)
  3. fallback ที่ดีควรข้ามค่าย/ข้ามโควตา — ของคุณตอนนี้: หลักเดินผ่าน Nous สำรองเดินผ่าน OpenRouter = ล่มไม่พร้อมกัน ยิ่งอนาคตเพิ่ม Google AI Studio เป็นชั้นสามยิ่งแน่น เพราะสามโควตาจากสามค่าย

จัดการ fallback chain ครบวงจร: ดู · เพิ่ม · ลบ · ล้าง

ต้องการคำสั่ง (เอกสารทางการ)
เปิดตัวจัดการแบบโต้ตอบ (ทำได้ทุกอย่างในที่เดียว)hermes fallback
ดูแถวปัจจุบันhermes fallback list (ย่อ: ls)
เพิ่มตัวสำรองต่อท้ายแถวhermes fallback add — เข้าหน้าเลือก provider+โมเดล (หน้าเดียวกับ hermes model)
ลบตัวใดตัวหนึ่งออกhermes fallback remove (ย่อ: rm)
ล้างทั้งแถวhermes fallback clear
สลับลำดับ / แก้ละเอียดแก้ตรงในไฟล์: หมวด fallback_providers: ใน config.yaml — แต่ละตัวมีคู่ provider: + model: เรียงบน→ล่างตามลำดับรับไม้ (สลับบรรทัด = สลับลำดับ) — หรือสั่งในแชทแบบที่เคยทำก็ได้
# หน้าตาใน config.yaml
fallback_providers:
  - provider: openrouter
    model: poolside/laguna-s-2.1:free    # ตัวรับไม้คนแรก
  - provider: nous
    model: upstage/solar-pro4:free       # ตัวรับไม้คนที่สอง

ตัวอย่างการลบ (ลำดับเต็ม — ดูก่อน ลบ ตรวจหลัง):

hermes fallback list      # ① ดูแถวก่อน: 1. poolside  2. solar-pro4
hermes fallback remove    # ② เมนูโต้ตอบเด้งให้เลือกตัวที่จะลบ → เลือก → ยืนยัน
hermes fallback list      # ③ ตรวจงาน: ต้องเหลือตามที่ตั้งใจ

หรือทางแชทประโยคเดียว: "ลบ upstage/solar-pro4:free ออกจาก fallback chain แล้วโชว์แถวที่เหลือยืนยัน" — กติกาเดิมเสมอ: ดูก่อนลบ และตรวจหลังลบ (บางเวอร์ชันรับชื่อเป็น argument ได้เลย — เช็คด้วย hermes fallback remove -h)

พฤติกรรมที่ควรรู้ (จากเอกสาร + สนามจริง)

① fallback ทำงานรายเทิร์น: ข้อความใหม่ทุกครั้งลองตัวหลักก่อนเสมอ ตัวหลักฟื้นเมื่อไหร่ระบบกลับไปใช้เอง ไม่ต้องสลับมือ ② ในหนึ่งเทิร์น fallback เด้งได้ครั้งเดียว ③ เงื่อนไขที่ trigger: 429 / 5xx (หลัง retry จนหมด), 401 / 403 / 404 (ทันที), คำตอบเสียรูปซ้ำๆ — และย้ำจากที่เราพิสูจน์เอง: timeout ไม่อยู่ในรายการ จึงต้องให้ cron ใช้โมเดลเสถียรตั้งแต่ต้น

ลำดับการเลือกโมเดลของงาน cron (พิสูจน์แล้วในสนามจริง)

1. cron.model ใน config.yaml     ← เครื่องเราล็อกไว้: poolside/laguna-s-2.1:free
2. ถ้าไม่ได้ตั้ง → ค่า global
3. ล้มระหว่างทาง → ไล่ fallback chain (global)
✗ ผ้าคลุมจากแชท (/model ใน Telegram) — cron ไม่เห็นและไม่ใช้เด็ดขาด

เพราะงาน cron ทุกรอบคือ session เกิดใหม่สด (กฎเหล็กบท 07) มันจึงไม่รู้จักแชทของเรา ไม่เห็นประวัติ และไม่เห็น override ที่แชทตั้งไว้ — ผลคือเกราะสองชั้น: ในแชทจะเผลอคลุมโมเดลอะไรไว้ก็ตาม งานโพสต์อัตโนมัติของเพจไม่สะเทือน · กลับกัน ถ้าจะแตะ cron.model หรือ fallback chain (สองจุดเดียวที่กระทบ cron ได้ — แก้ผ่าน CLI/config เท่านั้น) ให้คิดถึงงานอัตโนมัติเสมอ

คิวโพสต์ไฟล์ ~/.hermes/page/queue.jsonl — บรรทัดละ 1 คำคม พร้อมสถานะบนเครื่องเรา ~ คือ /opt/data/home ซึ่งอยู่บน volume (พิสูจน์แล้วจากไฟล์จริง) — path นี้ต้องตรงกับที่เขียนใน skill page-queue เสมอ ห้ามมีสองคิว
งานโพสต์ (cron 08:00 / 19:00 ไทย)หยิบคำคม ready ตัวแรก → ทำรูป → โพสต์เพจ → เปลี่ยนสถานะเป็น posted → รายงานเข้า Telegramสองงานแยกกัน ใช้คู่มือเดียวกัน
ความรู้ทั้งหมดเก็บเป็น skills: quote-style (มีแล้ว), page-queue, quote-image, post-facebookcron แต่ละรอบไร้ความจำ — คู่มือคือความจำถาวรของระบบ

รูปแบบคิว 1 บรรทัด (jsonl = JSON บรรทัดละก้อน):

{"text": "ความสำเร็จไม่อยู่ที่จุดหยุด แต่อยู่ที่การเริ่มต้นใหม่ทุกวัน", "status": "ready", "added": "2026-08-25"}
{"text": "อุปสรรคคือสิ่งที่คุณเห็น เมื่อละสายตาจากเป้าหมาย", "author": "เฮนรี ฟอร์ด", "status": "ready", "added": "2026-08-25"}

บรรทัดที่มี author = คำสอนคนดัง (รูปจะวาด "— ชื่อผู้กล่าว" ให้) · ไม่มี = คำคมออริจินัลของเพจ

สถานะมีแค่ 2 ค่า: ready (รอโพสต์) → posted (โพสต์แล้ว + วันที่) — เรียบง่ายที่สุดที่ยังทำงานได้ครบ

ภารกิจที่ 1 — นิยามสไตล์เพจให้จบ

ตอบ 5 ข้อนี้ (ในใจหรือจดใส่กระดาษ) แล้วเอาคำตอบไปอัปเดต skill quote-style ผ่านแชทกับ Hermes:

  1. ชื่อเพจ ที่จะใช้จริง (ต้องใช้ตอนสร้างเพจบท 12 ด้วย)
  2. คนอ่านคือใคร — วัยไหน กำลังเจออะไรในชีวิต (เช่น วัยทำงานที่เหนื่อยกับงาน)
  3. ธีมคำคม 3–4 ธีม ที่เพจจะวนเวียน (เช่น ความพยายาม / การเริ่มใหม่ / ใจเย็นกับตัวเอง)
  4. ตัวอย่างที่ใช่ 2–3 อัน (จากที่ Hermes เคยเสนอก็ได้) และตัวอย่างที่ไม่ใช่ พร้อมเหตุผลสั้นๆ
  5. ลายเซ็นเพจ — อยากให้ทุกโพสต์ลงท้ายด้วยอะไรไหม (เช่น ชื่อเพจ, #แฮชแท็กประจำ)

สร้าง skill ชื่อ page-queue เนื้อหา: วิธีจัดการคิวโพสต์ของเพจ
- คิวอยู่ที่ไฟล์ ~/.hermes/page/queue.jsonl (ถ้ายังไม่มีโฟลเดอร์/ไฟล์ ให้สร้าง)
- 1 บรรทัด = 1 คำคม รูปแบบ: {"text": "...", "status": "ready", "added": "YYYY-MM-DD"}
- เมื่อผู้ใช้พิมพ์ "เลือก" ตามด้วยหมายเลข: เอาคำคมหมายเลขนั้นจากชุดล่าสุดที่เสนอ เพิ่มเข้าคิวสถานะ ready แล้วตอบยืนยันจำนวนคิวคงเหลือ
- เมื่อโพสต์แล้ว: แก้ status เป็น posted และเพิ่ม "posted": "YYYY-MM-DD HH:MM"
- ห้ามลบบรรทัดออกจากไฟล์ ห้ามแก้ข้อความคำคมเอง

ตรวจงาน: สั่ง "ทดสอบ: เพิ่มคำคม 'ทดสอบระบบคิว' เข้าคิว แล้วโชว์เนื้อไฟล์ queue.jsonl ทั้งหมด" — เห็นบรรทัด JSON โผล่มา = ผ่าน

ขั้นที่ 1 — สร้างเพจ (5 นาที)

  1. เข้า facebook.com/pages/create ด้วยบัญชีส่วนตัวของคุณ
  2. ตั้งชื่อเพจ (ตามที่ตอบไว้บท 09) เลือกหมวดหมู่ (เช่น "ชุมชน" หรือ "เว็บไซต์ข่าวสารและสื่อ")

ขั้นที่ 2 — สร้าง Meta App (ประตูสู่ API)

  1. เข้า developers.facebook.com → ยอมรับเงื่อนไขนักพัฒนา (ใช้บัญชี Facebook เดิม)
  2. My Apps → Create App → ตั้งชื่อแอป (เช่น "QuotePage Poster") → ขั้น "กรณีการใช้งาน": รายการแนะนำจะไม่มีของเรา — คลิก filter "การจัดการเนื้อหา" ทางซ้าย แล้วเลือก "จัดการทุกอย่างบนเพจของคุณ" (Manage everything on your Page) → ขั้น "ธุรกิจ" ข้ามได้ → ยอมรับข้อกำหนด → สร้างแอป (ยืนยันกับหน้าจอจริง 2026-08-25)
  3. ใน Dashboard: use case จะมี permissions พื้นฐานติดมา (business_management, pages_show_list, public_profile) — กด Customize/ปรับแต่ง แล้วเพิ่ม pages_manage_posts + pages_read_engagement
  4. แอปเริ่มใน Development mode — โหมดนี้ใช้ทดสอบโพสต์ลงเพจตัวเองได้ แต่มีกับดักใหญ่: โพสต์ที่สร้างตอน dev mode จะถูกซ่อนจากคนทั่วไป (เห็นเฉพาะคนที่มีบทบาทในแอป — เจอจากเพจจริง: โพสต์ขึ้นแต่คนอื่นมองไม่เห็น) → พอทดสอบผ่านแล้วต้องทำขั้น "เผยแพร่แอปเป็น Live" ท้ายบทนี้

ขั้นที่ 3 — ขอกุญแจ (Page Access Token)

ใช้เครื่องมือทางการชื่อ Graph API Explorer (เมนู Tools ของ developers.facebook.com) · ต้องมี: แอปพร้อม App ID และ App Secret (ดูได้ใน App settings → Basic)

  1. ตั้งค่าฝั่งขวาก่อน — ช่อง "แอพ Meta" เลือกแอปของเรา (Quote Hermes) → ช่อง "ผู้ใช้หรือเพจ" เลือก "รับโทเค็นของผู้ใช้" (User Token) ⚠️ ใน dropdown นี้จะมีชื่อเพจให้เลือกด้วย — ห้ามเลือกเพจตรงนั้น (จะได้ Page token อายุสั้น ทางลัดที่พาลงเหว) → แท็บ Permissions ช่อง "เพิ่มสิทธิ์การอนุญาต" ใส่ให้ครบ 3 ตัว: pages_show_list, pages_manage_posts, pages_read_engagement (ตัว pages_show_list ขาดแล้ว me/accounts จะตอบว่างเปล่า)
  2. สร้าง User token ระยะสั้น — กด Generate Access Token → หน้าต่างล็อกอิน/อนุญาตเด้ง → ตอนถามว่าให้สิทธิ์เพจไหน เลือกเฉพาะ "บทเรียนชีวิต" → อนุญาตจนจบ token จะโผล่ในช่อง "โทเค็นการเข้าถึง"
  3. ต่ออายุเป็น 60 วัน — กดไอคอน ⓘ ตรงหัวช่อง token → Open in Access Token Tool (เด้งไปหน้า Access Token Debugger) → กดปุ่ม Extend Access Token ด้านล่าง (ถ้าขอ App Secret: ก๊อปจาก App settings → Basic ของแอป) → ได้ token ใหม่อายุ ~60 วัน — คัดลอกเก็บไว้
  4. เรียก me/accounts — กลับมาที่ Explorer ลบ token เดิมในช่องออกให้หมด แล้ววาง token 60 วันแทน (จุดที่คนพลาดบ่อยสุด) → ช่อง endpoint กลางบน: ลบของเดิม (เช่น me?fields=id,name) พิมพ์ me/accounts → เมธอด GET → เวอร์ชันตามที่ระบบตั้ง (เช่น v26.0 — จดเลขนี้ไว้ใช้ระบุใน skill ตอนบท 13) → กดปุ่ม ส่ง → ผล JSON: หา block ที่ "name": "บทเรียนชีวิต" → ก๊อป access_token (ยาวมาก เอาให้ครบ) และ id (= Page ID) — นี่คือ Page token ที่ไม่มีวันหมดอายุ
  5. ตรวจว่าไม่มีวันหมดอายุจริง — ก๊อป Page token ไปวางใน Access Token Debugger อีกครั้ง → บรรทัด Expires ต้องขึ้นว่า Never — ถ้าขึ้นเป็นวันที่ แปลว่าเผลอใช้ token สั้นตอนเรียก me/accounts ให้ย้อนทำข้อ 2–3 ใหม่
  6. เก็บให้ปลอดภัย — Page token + Page ID ลงไฟล์ /opt/data/.env ตามกล่องถัดไป — ห้ามลงโค้ดที่ push ขึ้น git ห้ามวางในแชท ใครได้ token นี้ไปโพสต์ในนามเพจคุณได้ทันที
สองจุดที่คนติดบ่อยในขั้นนี้

① ขาด pages_show_list → me/accounts ตอบว่างเปล่า (ไม่ error ด้วย งงกันมานักต่อนัก) ② ลืมวาง token 60 วันทับตัวเก่าก่อนเรียก me/accounts → ได้ Page token แบบมีวันหมดอายุโดยไม่รู้ตัว — ขั้นตรวจ Expires: Never ในข้อ 4 คือตาข่ายกันพลาดของทั้งสองจุดนี้

เก็บกุญแจให้ถูกที่

token นี้โพสต์ลงเพจคุณได้ = ความลับระดับเดียวกับ API key — เก็บในไฟล์ความลับของ Hermes: /opt/data/.env (ที่เดียวกับ Telegram token) โดยเพิ่มใน terminal ไม่ผ่านแชท: echo 'FB_PAGE_TOKEN=ค่าจริง' >> /opt/data/.env และ FB_PAGE_ID อีกบรรทัด — ระวัง: ใช้ >> (ต่อท้าย) ห้ามใช้ > ตัวเดียว (เขียนทับทั้งไฟล์!) · ส่วนคำสั่ง hermes secrets เป็นตัวเชื่อม Bitwarden/1Password — เราไม่ได้ใช้

ขั้นที่ 5 — เผยแพร่แอปเป็น Live (ไม่งั้นโลกไม่เห็นโพสต์!)

โพสต์ทดสอบผ่านแล้ว แต่ตราบใดที่แอปยังเป็น Development mode คนทั่วไปจะมองไม่เห็นโพสต์ที่แอปสร้าง (อาการ: โพสต์ขึ้นปกติ แต่คนอื่นเปิดเพจแล้วว่างเปล่า) — ต้องสลับเป็น Live ซึ่งไม่ใช่การส่งแอปตรวจ (App Review) · เส้นทางจริงที่ผ่านการพิสูจน์ (2026-08-26):

  1. หา Privacy Policy URL — Meta ขอลิงก์หน้านโยบายความเป็นส่วนตัวที่เข้าถึงได้จริง ทางเร็ว: ตัวสร้างฟรี เช่น freeprivacypolicy.com (กรอกชื่อแอป ได้ลิงก์โฮสต์ฟรี ใช้ยื่น Meta ได้จริง) — อนาคตย้ายไปโฮสต์บนโดเมนตัวเอง (บท 06) ให้ดูโปรขึ้นได้
  2. App settings → Basic: วาง Privacy Policy URL + เลือก Category → เลื่อนลงล่างสุดกด Save changes (จุดที่คนวางลิงก์แล้วลืมกด Save บ่อยมาก)
  3. ด่านทดสอบกรณีการใช้งาน — แดชบอร์ดแอปมีเช็คลิสต์ 3 ข้อ (ปรับแต่ง use case / ทดสอบ / เผยแพร่) ข้อ "ทดสอบ" ต้องการให้ permission หลักถูกเรียกใช้จริงอย่างน้อย 1 ครั้ง — การใช้งานจริงของเรานับอยู่แล้ว (โพสต์รูป = pages_manage_posts, เรียก me/accounts = pages_show_list) ไม่ต้องยิงเพิ่มเอง แต่ตัวนับหน่วงได้ถึง 24 ชั่วโมง — โพสต์ทดสอบวันนี้ พรุ่งนี้เช็คลิสต์ถึงเขียว อย่าตกใจถ้ายังเป็น 0 ทั้งที่โพสต์ไปแล้ว
  4. กดเผยแพร่ — เมนู "เผยแพร่" → เมื่อเงื่อนไขครบ ปุ่มน้ำเงิน "เผยแพร่" จะโผล่มุมขวาล่างของหน้า (ก่อนหน้านั้นไม่มีปุ่มเลย ไม่ใช่ปุ่มเทา) → กด → ขึ้นกล่อง "เผยแพร่แอพของคุณสำเร็จ 🎁" → สถานะข้างเมนูเปลี่ยนเป็น "เผยแพร่แล้ว"
  5. ทดสอบแบบคนนอก: เปิดเพจใน incognito (ไม่ล็อกอิน) — เห็นโพสต์ = ผ่านจริง · ผลจริงจากเพจเรา: หลัง Live แล้วโพสต์เก่าที่สร้างช่วง dev mode กลับมามองเห็นได้ด้วย ไม่ต้องลบทำใหม่ (ดีกว่าที่กังวลไว้)
แยกให้ออก: Live ≠ App Review

Live = เปิดสวิตช์ให้เนื้อหาที่แอปสร้างมองเห็นได้สาธารณะ (ทำเองได้ทันที แค่มี privacy policy) · App Review = ส่ง Meta ตรวจเพื่อให้คนอื่นมาใช้แอปเราได้ (Advanced Access) — ระบบเราแอดมินใช้เอง Standard Access พอ ไม่ต้องส่งตรวจ

Hermes ออกเวอร์ชันใหม่เรื่อยๆ — ลำดับที่ถูกคือ backup ก่อน อัปเดตทีหลัง: ทำ backup ชั้นในเครื่อง → เข้า hPanel → Docker Manager → อัปเดต image ของ Hermes project → container ถูกสร้างใหม่จาก image ใหม่ แต่ /opt/data อยู่ครบเพราะเป็น volume (บทที่ 03 สัญญาไว้ — ตรงนี้แหละที่มันจ่ายคืน) → ทดสอบทักบอท 1 ครั้ง + hermes doctor

💰 ศาสตร์การตัดสินใจจ่าย — 4 คำถามก่อนควักเงิน

  1. "ฟรีแพ้ตรงไหน วัดได้ไหม?" — จ่ายเมื่อมีหลักฐาน ไม่ใช่เมื่ออยากได้ของแรง และเรามีมิเตอร์วัดอยู่แล้วโดยไม่รู้ตัว: อัตราการกดเลือกของคุณตอนเช้า — ถ้าจาก 6 ข้อคุณเลือกได้แค่ 1 หรือปัดตกบ่อยเพราะภาษาแข็ง/ผิดกติกา = ฟรีกำลังแพ้ · ถ้าเลือกได้ 2–3 ทุกเช้าสบายๆ = ฟรีชนะอยู่ ไม่ต้องจ่าย
  2. "ต้นทุนจริงเดือนละเท่าไหร่?" — คำนวณก่อนเสมอ (เลขจริงของระบบเรา): งานคำคมเช้าใช้ ~3–5k tokens/รอบ × 30 วัน ≈ 150k tokens/เดือน → โมเดลจ่ายเงินราคา ~$0.2/1M input + $0.8/1M output ≈ ไม่ถึง $0.15/เดือน = ห้าบาท — ราคาต่อ token แทบไม่ใช่ประเด็น! ตัวที่ฆ่ากระเป๋าจริงคือ 3 อย่างจากเคส $5: context บวม × งานวนลูป × ผ้าคลุมค้างผิดที่
  3. "จ่ายเฉพาะจุดได้ไหม?" — ได้และควร: อัปเกรดเฉพาะงานที่คุณภาพคือหัวใจ (cron.model ของงานเขียนคำคม) ส่วนงาน mechanical (ทำรูป/โพสต์) ฟรีดีอยู่แล้ว — สถาปัตยกรรมเราแยกให้ตั้งแต่บทเสริม 7.5
  4. "ตาข่ายกางครบหรือยัง?" — ก่อนเปิดใช้ตัวจ่ายเงิน: เพดาน key ($1 ของเราตั้งแล้ว ✓) + fallback เป็นตัวฟรี ✓ + weekly-guard จับโมเดลแพงแปลกปลอม ✓ — ครบแล้วทดลองได้อย่างปลอดภัย: เปิด 1 สัปดาห์ วัดอัตราการกดเลือกเทียบก่อน-หลัง แล้วตัดสินด้วยตัวเลข

📚 Glossary — ศัพท์ประจำคอร์ส

ทุกบทเรียนใช้ศัพท์ตามนี้ เจอคำไหนไม่คุ้นให้กลับมาที่นี่ (เพิ่มคำใหม่ทุกครั้งที่บทเรียนแนะนำศัพท์ใหม่ · ล่าสุด: บทที่ 06)

VPS
Virtual Private Server — "คอมพิวเตอร์เช่า" ใน data center เปิดตลอด 24 ชม. เราได้สิทธิ์ควบคุมเต็ม จ่ายรายเดือน ระบบเพจคำคมทั้งหมดอาศัยอยู่บนเครื่องนี้
Server (เซิร์ฟเวอร์)
คอมพิวเตอร์ที่เปิดทิ้งไว้เพื่อ "ให้บริการ" เครื่องอื่น — ไม่มีจอไม่มีเมาส์ สั่งงานผ่านอินเทอร์เน็ต
Ubuntu
ระบบปฏิบัติการตระกูล Linux ที่นิยมสุดสำหรับเซิร์ฟเวอร์ (คอมบ้านใช้ Windows, เซิร์ฟเวอร์เราใช้ Ubuntu) — ฟรี เครื่องมือแทบทุกตัวรองรับเป็นอันดับแรก
SSH
Secure Shell — วิธีรีโมตเข้าไปสั่งงาน VPS จากคอมเราแบบเข้ารหัส สิ่งที่เห็นคือหน้าจอดำไว้พิมพ์คำสั่ง (ใช้จริงในบทที่ 02)
Terminal / Shell
หน้าจอข้อความล้วนไว้พิมพ์คำสั่งให้เครื่องทำงาน (บน Windows คือ PowerShell, บน VPS คือ shell ของ Ubuntu) — ไม่มีเมาส์ แต่ทำได้ทุกอย่าง
root
ผู้ใช้สิทธิ์สูงสุดของเครื่อง Linux — ทำได้ทุกอย่างรวมถึงลบทั้งระบบ ใช้ด้วยความระมัดระวัง Hostinger ให้เรา login เป็น root ตั้งแต่แรก
Prompt
บรรทัดล่างสุดของ terminal ที่รอเราพิมพ์ เช่น root@srv123:~# — อ่านว่า "user root อยู่บนเครื่อง srv123 ที่โฟลเดอร์ ~ (บ้าน)"
Docker
เครื่องมือที่ห่อโปรแกรมพร้อมทุกอย่างที่มันต้องใช้ไว้ใน "กล่อง" เรียกว่า container — ติดตั้งง่าย ลบง่าย ไม่ทำเครื่องรก Hermes รันอยู่ใน container
Container
กล่องที่ Docker สร้างมารันโปรแกรมหนึ่งตัวแยกส่วนจากระบบหลัก — พังก็ลบสร้างใหม่ได้โดยไม่กระทบเครื่อง
Image
แม่แบบสำเร็จรูปของโปรแกรมที่ใช้สร้าง container — image เดียวสร้างได้หลาย container (อุปมา: สูตรอาหาร → จานอาหาร)
Volume
ลิ้นชักเก็บข้อมูลถาวรนอก container — ลบ/อัปเดต container แล้วข้อมูลใน volume ไม่หาย ความจำของ Hermes อยู่ที่นี่
Docker Hub
คลังกลางบนอินเทอร์เน็ตที่รวม image ให้ดาวน์โหลด — docker run จะไปหยิบ image จากที่นี่ถ้าในเครื่องไม่มี
Docker Manager
หน้าเว็บใน hPanel ของ Hostinger ไว้จัดการ Docker ด้วยการกดปุ่ม — มี Catalog แอปสำเร็จรูปรวมถึง Hermes Agent
Hermes Agent
AI agent ของ Nous Research ที่รันบนเครื่องเราเอง — คุยผ่าน Telegram ได้ ตั้งงานอัตโนมัติ (cron) ได้ สอนทักษะใหม่ (skill) ได้ และจำสิ่งที่เรียนรู้ นี่คือ "พนักงาน" ของเพจเรา
AI Agent
โปรแกรม AI ที่ไม่ได้แค่ตอบคำถาม แต่ลงมือทำงานได้เอง — เรียกใช้เครื่องมือ ตัดสินใจ ทำงานหลายขั้นต่อเนื่องจนจบ

Large Language Model — "สมอง" ที่ agent ใช้คิด เช่นโมเดลตระกูล Claude, GPT, Hermes ต้องต่อ API key ของผู้ให้บริการโมเดล (มีค่าใช้จ่ายตามการใช้งาน)
Cron
ระบบตั้งเวลางานอัตโนมัติ — "ทุกวัน 07:00 ทำสิ่งนี้" Hermes มี cron ในตัว เป็นหัวใจของการโพสต์วันละ 2 ครั้ง
Domain (โดเมน)
ชื่อจำง่ายที่ชี้ไปยังเครื่องเรา เช่น mypage.com แทนเลข IP — Hostinger แถมฟรี 12 เดือน
IP Address
เลขประจำเครื่องบนอินเทอร์เน็ต เช่น 145.79.12.88 — ใช้ตอน SSH เข้าเครื่อง
HTTPS
การเข้าเว็บแบบเข้ารหัส (รูปกุญแจ 🔒 หน้า URL) — จำเป็นเมื่อเปิดหน้าเว็บ Hermes ให้เข้าจากอินเทอร์เน็ต
API
Application Programming Interface — "ประตูหลังบ้าน" ให้โปรแกรมคุยกับบริการต่างๆ โดยไม่ต้องเปิดหน้าเว็บ เช่น Hermes โพสต์ลงเพจผ่าน Facebook Pages API
Pipeline
สายพานงานหลายขั้นต่อกัน — ของเราคือ หาคำคม → เลือก → เข้าคิว → ทำรูป → โพสต์
Human-in-the-loop
จุดที่ระบบอัตโนมัติหยุดรอ "คน" ตัดสินใจก่อนไปต่อ — ของเราคือขั้นที่คุณกดเลือกคำคมใน Telegram
API key
รหัสลับไว้ใช้บริการผ่าน API — เหมือนบัตรเครดิตย่อมๆ ใครได้ไปก็เผาเงินเราได้ ห้ามแชร์ และตั้งเพดานใช้จ่ายเสมอ
Bot (Telegram) / BotFather
บอทคือบัญชี Telegram สำหรับโปรแกรม — "เบอร์โทร" ที่ Hermes ใช้รับข้อความ สร้างผ่าน @BotFather (บอททางการของ Telegram) ซึ่งออก token ให้
Gateway (Hermes)
ตัวกลางของ Hermes ที่ต่อกับช่องทางสื่อสาร (Telegram ฯลฯ) และคอยปลุก cron — ต้องรันค้างไว้ตลอด ระบบถึงตอบแชทและทำงานตามเวลาได้
Traefik
"พนักงานต้อนรับ" หน้าประตูเว็บของเครื่อง — รับผู้เข้าชม พาไปยัง container ที่ถูกต้อง และขอใบรับรอง HTTPS ให้อัตโนมัติ (Hostinger ติดมาให้ตอน deploy Hermes)
DNS
Domain Name System — สมุดโทรศัพท์ของอินเทอร์เน็ต แปลงชื่อโดเมน → เลข IP
A record
บรรทัดหนึ่งในสมุด DNS ที่ประกาศว่า "ชื่อนี้ = IP นี้" — เราใช้มันชี้โดเมนฟรีเข้า VPS
Propagation
ช่วงเวลาที่การแก้ DNS ค่อยๆ กระจายไปทั่วโลก — ทางการบอกได้ถึง 24 ชม. ส่วนใหญ่เร็วกว่านั้นมาก
Skill (Hermes)
คู่มืองานหนึ่งเรื่องในไฟล์ SKILL.md เก็บที่ /opt/data/skills/ (เครื่องเรา — ค่ามาตรฐานเอกสารคือ ~/.hermes/skills/) — ความจำถาวรของระบบ ผูกกับงาน cron ได้ สร้างผ่านแชท, /learn, หรือ hermes skills install
Self-contained prompt
คำสั่งที่จบในตัวเอง ไม่พึ่งความจำจากแชทเก่า — จำเป็นสำหรับงาน cron เพราะทุกรอบเป็น session สด
UTC / Timezone
เซิร์ฟเวอร์มักตั้งนาฬิกาเป็น UTC ซึ่งช้ากว่าไทย 7 ชั่วโมง — เช็คด้วย date ก่อนตั้งงานตามเวลาเสมอ
Queue (คิวโพสต์)
ไฟล์ ~/.hermes/page/queue.jsonl — คำคมที่คุณเลือกแล้วรอโพสต์ บรรทัดละอัน สถานะ ready → posted
Graph API
API หลักของ Meta — ระบบเราใช้ endpoint /{PAGE_ID}/photos โพสต์รูปลงเพจ (ระบุเวอร์ชัน API เสมอ)
Page Access Token
กุญแจสิทธิ์โพสต์ลงเพจ ได้จาก user token อายุยาวผ่าน me/accounts — ตัวจากอายุยาวจะไม่หมดอายุ เก็บใน hermes secrets
Development mode (Meta App)
โหมดเริ่มต้นของแอป Meta — โพสต์ลงเพจที่เราเป็นแอดมินได้เลยโดยไม่ต้องส่งแอปตรวจ พอสำหรับระบบส่วนตัวแบบเรา
Fallback chain
แถวโมเดลสำรองที่รับไม้ต่ออัตโนมัติเมื่อโมเดลหลักล้ม (429/เครดิตหมด/error) — ตั้งด้วย hermes fallback, ห้ามซ้ำกับตัวหลัก, ควรอยู่คนละค่าย/โควตา
ไฟล์ .env (Hermes)
ที่เก็บความลับจริงของ Hermes: /opt/data/.env — token/key ทุกตัวอยู่ที่นี่ (Telegram, Facebook) เพิ่มด้วย echo '...' >> ใน terminal ไม่ผ่านแชท · ส่วนคำสั่ง hermes secrets คือตัวเชื่อมตู้เซฟภายนอก (Bitwarden/1Password) ซึ่งคอร์สนี้ไม่ใช้

🛠 เทคนิค & Workflow ประจำระบบ

คู่มือภาคสนาม — ทุกข้อในหน้านี้มาจากเหตุการณ์จริงที่เราเจอและแก้ด้วยกันในคอร์ส ไม่ใช่ทฤษฎี (อัปเดตเรื่อยๆ เมื่อเจอบทเรียนใหม่)

1. ศิลปะการสั่งงาน agent

เทคนิคตัวอย่าง / เหตุผล
บอกทั้ง "ทำอะไร" และ "ห้ามทำอะไร""...เป็นข้อความผลลัพธ์โดยตรง ห้ามสร้างหรือเรียกใช้สคริปต์ใดๆ" — เกิดจากเคสงาน cron แรกที่ agent สร้างสคริปต์เกินจำเป็นจน path พัง
ให้ทางออกปลอดภัยเสมอ"ถ้าหาของจริงไม่ครบ 3 ข้อ ให้ลดจำนวนแล้วเติมออริจินัลแทน" — ถ้าไม่ให้ทางลง agent จะ "ขยัน" กุข้อมูลมาให้ครบ
แก้พฤติกรรม = แก้ที่ skill ไม่ใช่บ่นในแชทเจอคำคมภาษาจีนปน → "อัปเดต skill quote-style เพิ่มข้อห้าม..." — คู่มือคมขึ้นถาวร บ่นในแชทหายไปกับ session
ให้ agent ซ่อมงานตัวเองสูตร: แปะ error จริง + บอกเป้าหมาย + สั่ง "แก้เสร็จรันทดสอบให้ดู" — เคส script path พัง มันลบงานเสีย สร้างใหม่ ทดสอบ ยืนยัน ครบใน 1 คำสั่ง
วนงานภาพเหมือนคุยกับกราฟิก"ขยับข้อความขึ้น" / "ห้ามหักกลางคำ ตัดได้เฉพาะช่องว่าง" — สั่งแก้เป็นรอบๆ จากสิ่งที่เห็น ไม่ต้องพยายามสั่งครบในรอบเดียว
path เต็มเสมอใน skill/opt/data/home/.hermes/page/... ไม่ใช่ ~/.hermes/... — shell กับ agent session ตีความ ~ คนละที่ (พิสูจน์แล้วบนเครื่องนี้)
ตรึงคำสั่งที่พิสูจน์แล้วลงใน skillขั้นตอนสำคัญ (เช่น curl ยิง API) ต้องเขียนคำสั่งเป๊ะๆ ในคู่มือ ไม่ปล่อยให้ cron "ประกอบใหม่เอง" ทุกรอบ — เคสจริง: โพสต์จากแชทสำเร็จ แต่ cron ประกอบ request เองแล้วโดน 403 พร้อมเดาคำอธิบายผิดๆ (publish_actions) มาเล่า
งานคำตอบยาว = หั่นเป็นรอบย่อยAPI call มีเพดานเวลา (90s แบบ non-streaming) — งานที่ output ใหญ่ (เช่น แผน 14 ช่อง) จะ timeout ซ้ำๆ และ fallback ช่วยไม่ได้เพราะเจอโจทย์ก้อนเดิม → สั่งในงานให้ "ร่างทีละครึ่ง แล้วรวมส่ง ห้ามสร้างทั้งหมดในครั้งเดียว" (เคสจริง: weekly-plan ล้ม 3 ครั้งติด หายขาดหลังหั่นครึ่ง)

4. หลักการเลือกโมเดล

  1. งานแชทใช้โมเดลฉลาดสุด งานอัตโนมัติใช้โมเดลเสถียรสุด — cron 07:00 ไม่มีใครนั่งกดรันซ้ำ ความนิ่งชนะความหรู (ตั้งแยกด้วย cron.model ใน config.yaml)
  2. fallback ต้องข้ามค่าย/ข้ามโควตา — สำรองค่ายเดียวกันกันได้แค่ "โมเดลแน่น" กัน "เพดานบัญชี" ไม่ได้
  3. รู้จุดบอดของโมเดลฟรี: ภาษาอื่นปนได้ (จีน/เกาหลี/อังกฤษ), กุคำคม+กุคนได้, timeout ได้ — และ timeout ไม่ trigger fallback (ข้อจำกัดจริงของ Hermes ที่เราค้นพบเอง)
  4. ⚠️ กับดัก "session only" ในแชทถาวร (บทเรียนราคา $5): การสลับโมเดลด้วย /model ใน Telegram ขึ้นป้าย "session only" ฟังดูชั่วคราว — แต่แชท Telegram คือ session เดียวยาวไม่มีวันจบ = ถาวรโดยพฤตินัย เคยเผลอเลือกโมเดลเสียเงิน (GPT-5.6 Luna) ไว้ ทุกงานที่สั่งผ่านแชทหลายวันจ่ายเงินหมดโดย hermes model ฝั่ง CLI ยังโชว์ค่า global ที่ไม่ถูกใช้ — กฎ: (1) เช็คโมเดลใช้จริงจาก log ฝั่ง provider เป็นระยะ อย่าเชื่อ config (2) ตั้ง Credit limit บน API key ที่เว็บ provider เสมอ (3) session แชทบวม (90k token/ครั้ง) ให้เริ่มบทสนทนาใหม่ — ความจำถาวรอยู่ใน skills ไม่หาย

5. กฎความปลอดภัย & คุณภาพ

  1. ความลับทุกชนิด (API key, bot token, FB token) → เก็บในไฟล์ /opt/data/.env โดยพิมพ์เพิ่มใน terminal เท่านั้น — ห้ามแปะในแชท (จะวิ่งผ่าน LLM) ห้ามฝังในไฟล์ skill · เพิ่มด้วย >> เสมอ ห้าม > ตัวเดียว
  2. คำคมคนดัง: Google ก่อนเลือกเสมอ · ชื่อที่ไม่รู้จัก = ปัดตกทันที · ป้าย [ยืนยันแล้ว] ของ AI เชื่อไม่ได้ (เคสจริง: คำคมคานธีที่โลกแชร์แต่ไม่มีต้นทาง ก็ถูกแปะป้ายยืนยัน)
  3. ก่อนของใหม่เข้าระบบ ซ้อมด้วย cron run เสมอ — ทุกบั๊กที่เจอในคอร์สนี้ถูกจับตอนซ้อม ไม่ใช่ตอนจริง
